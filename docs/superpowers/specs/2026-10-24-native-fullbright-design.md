# RE8 FullBright — Steam Deck Native 설계안

- 작성일: 2026-10-24 (Asia/Seoul)
- 저장소: https://github.com/like-shock/RE8_FullBright
- 상태: **상세 설계 사용자 승인 완료 (2026-10-24)**
- 승인 범위: Native 중심 접근과 이 문서의 초기 범위·구현 구조·단계별 검증 기준. 실행 계획 작성으로 진행한다.
- 문서 범위: 구현 방향, 기능 범위, 조사·검증 기준, 개발 단계. 제품 코드 구현 및 실기 검증 완료를 뜻하지 않는다.
- 설계 검토: 2026-10-24 독립 빌더 검토에서 계획 수립을 막는 미결 질문 없음. 게임 내 실현 가능성 검증과는 별개다.

## 1. 목적과 승인된 방향

Steam Deck/Proton에서 Resident Evil Village(RE8)의 Fullbright를 켜면, 사용자가 장면마다 광량을 조절하지 않아도 어두운 실내·동굴·먼 공간의 지형과 사물을 식별할 수 있도록 한다. 가까운 벽이나 물체만 과도하게 밝아지는 손전등 증폭 방식은 목표에 맞지 않는다. 시각적 기준은 사용자가 확인한 RE7 OTS Fullbright의 효과다.

사용자가 확정한 사항:

- 코드와 개발 문서는 `like-shock/RE8_FullBright`에서 관리한다.
- 1차 실행·검증 환경은 Steam Deck/Proton이다.
- Lua 조명 실험을 먼저 반복하는 단계를 제외하고, **Native 구현을 기본 경로**로 삼는다.
- 구현보다 계획을 먼저 작성한다.

설계자가 정한 기본안(실측 또는 사용자 확정 사항과 구분):

- 첫 지원 범위는 Steam판 RE8의 **한 실행 파일 빌드**, 본편 1인칭, 게임 내 RT OFF다.
- 처음에는 밝기 효과를 한 장면에서 입증하고, 이후 대표 구간과 상태 전환으로 검증을 넓힌다.
- 로드 직후 기능은 OFF로 시작한다. 실행 중 토글은 가능하되, 재실행 자동 ON은 초기 범위에 넣지 않는다.
- 사용자가 조절할 밝기 슬라이더보다 검증된 기본 프로필 하나를 먼저 제공한다. 내부 실험 상수는 개발용으로만 유지한다.
- Steam Deck에서 빌드 도구를 설치할 필요 없이 Windows x64 DLL 설치 패키지를 받도록 한다.

## 2. 확인된 근거와 아직 모르는 것

RE7 기준 커밋은 `ffde226b12c76e3dfec806e8e0a23de267e2b6a5`로 고정한다.

### 확인된 사실

- RE7의 `native_fullbright.c`는 특정 광원을 식별해 반경·색상 관련 피연산자를 바꾸고, 밝기 관련 명령 경로도 함께 변경한다. 원본 명령 위치에서 CPU 레지스터 결과를 치환하는 구조다.
- 해당 구현은 조명 객체의 지속적인 값 덮어쓰기 대신 레지스터 치환을 사용한다. 원래 게임 명령에 포함된 스택 쓰기는 재현한다.
- 광원 소유자, 플레이어, 지역, 로딩·준비 상태가 바뀌면 추적 상태를 무효화한다. RE7의 카메라 구현에 연결된 조건도 포함되어 있다.
- RE7의 이전 Lua 기반 Explore 실패 기록은 주로 3인칭 카메라·판정 시점 불일치, 반복 SDK 호출, 상태 전달 문제에 관한 것이다. 이것만으로 RE8의 모든 Lua 조명 제어가 불가능하다고 결론 내리지는 않는다.
- RE7 Native의 설치·후킹·로그·빌드 기반과 테스트는 참고할 수 있으나, RE8에 대한 호환성 증거는 아니다.

### 확인되지 않은 사항

- 실제 대상 `re8.exe`의 빌드/해시, Proton 버전, REFramework 빌드, 그래픽 설정.
- RE8에 RE7과 같은 역할의 광원·활성 조건·렌더링 경로가 있는지.
- RE7에서 `GLOBAL_BRIGHTNESS` 등으로 명명한 위치가 RE8에서 어떤 계산에 대응하는지. 기존 이름을 엔진의 공식 의미로 취급하지 않는다.
- RE7의 수치와 처리 조합이 RE8에서 같은 화면을 만드는지, 밝은 구간과 장면 전환에서도 품질을 유지하는지.
- 전체 구간의 효과 및 Steam Deck 성능. 현재 설계 단계에서 성공률·FPS 수치는 측정되지 않았다.

이 설계는 `max(조명, 최소 주변광)` 같은 셰이더를 이미 적용할 수 있다고 가정하지 않는다. RE7도 그 수식으로 구현된 것은 아니다.

## 3. 검토한 접근과 선택 이유

| 접근 | 이점 | 부담/제약 | 결정 |
| --- | --- | --- | --- |
| A. Lua 속성 제어부터 실험하고 부족하면 Native 전환 | 필요한 속성이 노출되어 있다면 초기 변경이 작음 | 필요한 제어 지점의 존재가 미확인이고 RE7과 유사한 시행착오를 반복할 수 있음 | 주 개발 경로에서 제외 |
| B. RE7 동작을 참고한 RE8 Native 구현 | 실제로 효과가 확인된 처리와 제어 시점을 분석 출발점으로 사용 가능 | RE8의 대응 코드·객체를 새로 찾아야 하며 이식 성공은 미보장 | **사용자 승인** |
| C. 렌더링 셰이더에서 조명 계산 변경 | 목표 효과에 직접 접근할 여지가 있음 | 셰이더 식별·교체 및 렌더링 경로별 대응 범위가 큼 | 초기 범위 제외. Native 경로가 막히면 별도 재설계 |

Lua는 필요한 객체·타입 정보를 빠르게 읽는 제한된 보조 도구로만 사용할 수 있다. 별도의 Lua 조명 시제품이나 광량 튜닝 단계를 만들지 않는다. UI에 REFramework Lua 바인딩이 필요할 수 있다는 점은 광원 제어를 Lua로 구현한다는 뜻이 아니다.

## 4. 기능 범위

### 첫 효과 검증(MVP)

- 검증된 RE8 빌드에서만 로드·대상 검증·후킹을 수행한다.
- 어두운 장면 한 곳에서 Fullbright ON/OFF 비교가 가능하다.
- 가까운 물체와 먼 지형을 함께 비교한다. 효과가 손전등 방향·거리 변화에 지나치게 의존하면 목표 미달이다.
- OFF로 전환하면 해당 기능의 레지스터/분기 보정을 중지하고 게임의 원래 명령을 실행한다.
- 설치·대상 식별·적용 횟수·거부 사유를 구분해 기록한다.

### 안정화 범위

- 같은 기본 프로필로 실내, 동굴·지하, 밝은 야외를 비교한다.
- 시점 회전, 치료, 아이템 조사, 메뉴, 컷신, 로딩, 사망·재시작, 지역 이동 후의 상태를 검증한다.
- 기능 토글, 설정 저장, Steam Input에서 지정할 단축키, 수동 설치·제거 안내를 제공한다.
- 장면별 설정 조절 없이 사용자 목표에 부합하는지 판정한다.

### 초기 범위 밖

- 3인칭 카메라, 머리·모델 교체, 조준·충돌 제어, 게임의 시간대 변경.
- RT ON, DLC/추가 모드, VR, macOS/iOS 네이티브판, 모든 게임 빌드의 자동 지원.
- ReShade 프리셋, 카메라 부착 추가 광원, 광량을 계속 높이는 우회 기능.
- 전체 게임 무결점 보장, 정해진 FPS 보장, 즉시 완성 일정 약속.

## 5. 구현 구조

배포 단위는 `RE8_FullBright.dll`인 Windows x64 REFramework Native 플러그인으로 한다. 다음 경계를 둔다.

| 부분 | 책임 |
| --- | --- |
| 플러그인 수명·설정 | REFramework API 버전 확인, 초기화, 토글 요청, 현재 상태 표시 |
| 빌드 프로필 | 실행 파일 식별, 코드 구간·명령·패턴 검증, 지원 빌드와 검증 근거 연결 |
| 대상 매핑 | RE8의 조명 객체 식별, 소유자·세대·장면 변경 확인, 적용 가능한 명령 위치 정의 |
| 훅·명령 재현 | 원래 명령의 피연산자/부작용/분기를 보존하고, 검증된 대상에만 값 치환 |
| Fullbright 정책 | 사용자 요청, 실제 적용 가능 상태, 조명 처리 조합 관리 |
| 진단 | 적용/통과/실패 계수, 상태 변경 이벤트, 제한된 스냅샷과 파일 출력 |

### 언어·빌드 기본안

설계자 선택은 **C11 + 필요한 최소 x86-64 어셈블리**, Linux CI에서 Windows x64로 교차 빌드하는 방식이다. RE7의 기존 C 기반 훅 브리지와 검사 구조를 검토·재사용하기 위한 선택이다. REFramework의 C 플러그인 API 경계를 사용한다. 다른 언어로 재작성하는 것은 초기 목표가 아니다.

기존 `native_build.sh`와 ABI/브리지 검사를 참고하되 카메라·모델·원본 CT 전체를 복제하지 않는다. REFramework API 헤더, 훅 라이브러리, 컴파일러와 추가 라이브러리는 구현 계획에서 고정 버전/해시를 선정한다. SDK나 UI 통합 때문에 소규모 C++ 어댑터가 필요하면 빌더가 근거를 남겨 결정할 수 있다.

UI는 REFramework 메뉴의 ON/OFF와 상태 표시를 우선한다. RE7처럼 최소 Lua 메뉴 바인딩이 필요하면 허용하지만, 훅의 조명 연산·대상 탐색·로그 파일 왕복은 Lua에 맡기지 않는다. 별도 autorun 스크립트를 설치해야 하는 구조는 기본안이 아니다.

### 상태와 복원

- 사용자 ON 요청과 실제 적용 여부를 별도로 표시한다. 최소 상태는 `OFF`, `UNSUPPORTED_BUILD`, `WAIT_TARGET`, `ACTIVE`, `FAULT`다.
- `ACTIVE`는 훅 적용이 관측되었다는 뜻이다. 화면 품질이나 전체 장면 검증 통과를 뜻하지 않는다.
- 미지원 빌드/패턴 불일치에서는 조명 훅을 설치하지 않는다. 핵심 훅 묶음 검증이 실패하면 일부만 활성화하지 않는다.
- 사용자 OFF, 대상 수명 종료, 로딩·장면 변경, 객체 소유자 불일치에서는 원래 명령을 통과시키고 캐시를 무효화한다.
- 로딩 후에는 새 대상을 재확인한 뒤에만 ON 요청을 다시 적용한다. RE7의 지역 번호·플레이어 포인터 체인·카메라 준비 조건을 가져오지 않는다.
- 컷신·치료 시 무조건 꺼야 한다고 가정하지 않는다. 대상이 계속 유효하면 적용을 유지하고, 유효성을 보장할 수 없으면 원래 동작으로 복귀해 그 구간을 미지원으로 기록한다.
- OFF는 DLL을 실행 중 언로드한다는 뜻이 아니다. 안전한 통과 경로를 유지하며 설치 파일 교체와 제거는 게임 종료 후 수행한다.

## 6. RE7에서 RE8로 매핑할 대상

아래는 분석 시작점이며 RE8에도 같은 개수의 훅이 필요하다는 요구사항이 아니다.

| RE7 위치/동작 | RE8에서 확인할 것 |
| --- | --- |
| `LIGHT_SOURCE_DIAMETER_READ` | 처리 대상 광원 식별 기준, 실제 피연산자의 의미, 색/범위 관련 값이 소비되는 위치 |
| `LIGHT_RADIUS_MULSS_READ`, `LIGHT_RADIUS_MOVSS_READ` | 같은 광원의 범위 계산인지, 다른 광원으로 보정이 전파되지 않는지 |
| `EXAMINE_LIGHT_CMP_1`, `EXAMINE_LIGHT_CMP_2` | 대상 광원 활성 조건 및 조사·치료·일반 플레이 사이 수명 변화 |
| `GLOBAL_BRIGHTNESS`, `G_BRIGHTNESS_2` | 렌더링 계산의 실제 의미와 적용 범위, 노출·조명 변화에 대한 영향 |
| `OLD_HOUSE_BRIGHTNESS_READ` 보정 | RE8에서도 필요성이 있는지. RE7 특정 지역에 연결된 처리를 자동 이식하지 않음 |
| RE7 플레이어·지역·로딩 관측 | RE8에서 최소한으로 필요한 대상 수명·준비 조건. OTS 전체 상태기계는 제외 |

RE7의 AOB, 고정 주소, 객체 오프셋, 마커, 밝기 수치는 RE8의 검증값으로 쓰지 않는다. 같은 바이트가 한 곳에 검색되더라도 같은 기능이라고 인정하지 않는다.

각 후보의 근거에는 대상 모듈/빌드, 함수 주변 흐름, 원래 명령과 피연산자, 객체 소유 관계, 호출 조건, 레지스터·플래그·스택 부작용, 런타임 관측 결과를 남긴다. 필요한 레지스터 및 활성 CPU 확장 상태 보존, 명령 재배치와 원래 분기 재현, 스레드 간 공유 상태, 설치/철회 경로를 검사한다. 접근 위반을 잡아 무조건 계속 실행하는 방식은 성공 조건이 아니다.

## 7. 개발 단계와 전환 기준

| 단계 | 작업·산출물 | 다음 단계 조건 |
| --- | --- | --- |
| M0. 대상 고정 | 게임 해시/PE 정보, Proton·REFramework 버전, 그래픽 설정, 기준 장면 기록 | 실제 분석 가능한 실행 파일 또는 충분한 디스어셈블리·런타임 근거 확보 |
| M1. RE7 최소 의존성 분석·RE8 매핑 | 처리별 대응표, 후보 명령·대상·수명 검증 근거 | 효과 검증에 필요한 최소 후보 묶음이 근거와 함께 식별됨 |
| M2. 한 장면 효과 검증 | 기본 OFF인 실험 DLL, ON/OFF 비교, 적용·통과 로그 | 먼 어두운 곳의 식별력 개선, 가까운 물체의 과노출 억제, OFF 복귀를 실기로 확인 |
| M3. 수명·전환 안정화 | 로드·치료·조사·컷신·재시작 테스트 및 수정 | 동일 빌드에서 대상 교체 후 잘못된 적용·남은 보정 없음 |
| M4. 범위·성능 검증 | 대표 장면 결과표와 프레임 시간 비교 | 공통 기본값이 목표에 부합하고 성능 퇴행이 허용 범위에 있음 |
| M5. 설치 패키지 | ZIP, 체크섬, 빌드 정보, 설치·제거·제한사항 안내 | 검증한 소스 커밋과 바이너리 연결, 새 설치·갱신·제거 확인 |

### 조사 방식의 제한

별도 Probe 설치·여러 차례 로그 수집을 모든 구현의 필수 선행 조건으로 만들지 않는다. 정적 근거로 안전하게 구현할 수 있으면 M2 실험 DLL에 필요한 진단을 함께 넣는다.

런타임 관측이 꼭 필요하면 먼저 확인할 가설·필드·한 번의 재현 절차·종료 조건을 적는다. 결과가 가설을 지지하지 않으면 그 후보를 기각하며, 설명 없이 수집 범위를 계속 넓히지 않는다.

메타데이터/메모리를 읽기만 하는 조사와 **원래 명령을 통과시키는 계측 훅**을 구분한다. 후자는 조명 값을 바꾸지 않더라도 프로세스의 코드에 detour를 설치하므로 동일한 빌드·명령·ABI 검증이 필요하다.

새 정보로 목표 효과를 만들 수 없다고 판단되거나 대응 제어 지점을 찾지 못하면 현재 근거와 막힌 지점을 보고한다. 임의 오프셋·밝기 상수·자동 노출 조절을 추가하며 성공으로 처리하지 않는다. Native 경로를 떠나 셰이더 교체 등으로 범위가 바뀌면 새 설계를 제안한다.

## 8. 검증 기준

### 오프라인 검사

지원 빌드 검증, 패턴 중복/불일치 거부, 원본 명령 재현, 대상 일치/불일치, OFF 통과, 잘못된 피연산자·수명 변경, 설정·로그 한도, 패키지 구성을 검사한다. 새 훅의 입력/출력·레지스터/플래그·스택 결과는 가능한 한 실제 명령 대조로 확인한다. 구현을 그대로 정답으로 복사한 모의 검사만으로 동등성을 주장하지 않는다.

빌드 성공·모의 검사 통과·훅 적용 계수는 실제 렌더링 품질이나 Deck 성능의 증거가 아니다.

### 실기 비교 절차

같은 세이브/위치/카메라 방향/그래픽 설정에서 기본 화면, ON, OFF 복귀 순서로 비교한다. 가능하면 밝은/어두운 영역이 한 화면에 함께 보이는 장면을 포함한다. 게임 자체의 자동 노출이 안정되는 시간을 일정하게 두고, 모드가 노출 설정을 몰래 바꿔 비교를 왜곡하지 않게 한다.

| 항목 | 판정 기준 |
| --- | --- |
| 어두운 영역 | 기본 화면에서 식별이 어려운 사물·지형을 ON에서 확인 가능 |
| 가까운 밝은 물체 | 벽·손·무기·물체의 무늬/색이 과노출로 사라지지 않음 |
| 방향·거리 | 회전 중 손전등 같은 집중 영역이나 뚜렷한 밝기 경계가 생기지 않음 |
| OFF 복귀 | 장면 상태에 맞는 원래 조명으로 돌아오고 보정이 남지 않음 |
| 전환 | 치료·조사·컷신·로드 전후의 끊김과 미지원 구간을 명시적으로 기록 |
| 성능 | 같은 조건에서 OFF/ON/OFF를 각 60초 이상 비교, 프레임 제한·TDP·해상도·온도 조건을 기록 |

성능의 초기 검토 기준은 중앙값과 p95 프레임 시간 증가가 각각 10% 이내인 것으로 제안한다. 이는 보장이 아니다. 프레임 제한에 가려지는 비용은 별도 비교가 필요하며, 조건이 달라졌거나 표본이 부족하면 결론을 보류한다. 기준 초과 시 장면별 분석·최적화 또는 사용자와의 기준 재검토가 필요하고 자동으로 통과시키지 않는다.

시각적 성공은 사용자의 목표 부합 확인을 포함한다. 모든 대표 장면에 공통 기본값이 통하지 않으면 "전체 Fullbright 완성"으로 발표하지 않는다. 화면 결과는 통과/실패/미확인으로 구분하고 테스트하지 않은 구간은 미확인으로 남긴다.

## 9. 입력 자료와 역할

### 이후 구현에서 필요한 입력

- 대상 게임의 Steam 빌드 정보, 실행 파일 SHA-256과 PE 정보.
- SteamOS/Proton·REFramework 버전과 설치 상태, RT/해상도/프레임 제한 등 비교 설정.
- 정적 분석이 가능한 합법적으로 보유한 대상 실행 파일의 비공개 작업 사본, 또는 필요한 함수의 디스어셈블리와 최소 런타임 자료.
- 재현 가능한 어두운 장면·밝은 장면과 테스트 결과.

해시만으로 후킹 위치를 발견할 수는 없다. 정적/동적 분석 자료와 실기 환경이 모두 없으면 M1·M2를 완료했다고 주장하지 않는다. 게임 전체 실행 파일이나 원본 CT, 세이브, 덤프를 공개 Git에 올리는 방식은 사용하지 않는다. 실제 필요 자료의 전달 방법은 해당 단계에 안내한다.

현재 작업 환경에는 RE8 실기 접근이 확인되어 있지 않다. 개발자는 소스 분석·구현·빌드·오프라인 검사·결과 해석을 담당하고, Steam Deck에서의 실행·화면 확인은 사용자의 테스트 결과를 받아 진행하는 것을 기본으로 한다. 원격 실기 접근이 실제로 연결되면 그 범위에서 역할을 조정한다.

한 번의 테스트에는 바이너리 버전, 재현 절차, 기대 결과, 수집 파일을 함께 제공한다. 개발자가 로그를 자동 요약할 수 있게 구성해 사용자가 매번 수동으로 광량·주소·후킹 설정을 조절하도록 하지 않는다.

## 10. 진단·저장소·배포

- 진단에는 빌드/프로필 식별, 상태 전환, 훅별 호출·적용·통과·실패 계수, 필요한 최소 객체 식별 정보만 포함한다.
- 훅 안에서 파일 I/O·광범위한 SDK 탐색을 수행하지 않는다. 제한된 버퍼에 기록한 뒤 별도 경로에서 출력한다.
- 기본 로그는 두 파일을 순환하며 합계 8 MiB 이내로 제한한다. 출력 실패·버퍼 포화는 계수하고 게임 제어를 멈추지 않는다. 상세 계측은 선택 사항이다.
- `main`에는 검토된 문서와 통합 코드를 둔다. 실험은 `research/*`, 기능 개발은 `feature/*` 브랜치에서 관리하며 게임 검증 범위를 PR/문서에 남긴다.
- 이 저장소는 처음 비어 있었으므로 첫 문서 커밋으로 `main`을 시작한다. 이 문서 커밋은 제품 구현 승인을 뜻하지 않는다.
- 설계서는 `docs/superpowers/specs/`, 승인 후 상세 실행 계획은 `docs/superpowers/plans/`, 매핑 근거는 `docs/research/`, 실기 결과는 `docs/validation/`에 관리한다.
- 개인 로그·덤프·게임 파일·기존 CT 전체는 커밋하지 않는다. 분석 결과를 재현하는 데 필요한 최소 메타데이터와 요약만 남긴다.
- 기존 RE7 코드 재사용 시 파일별 출처·라이선스·원 저작자 표시를 검토한다. MinHook 등 의존성 고지와 바이너리 체크섬도 패키지에 포함한다.
- 불확실한 실험 결과물은 실험용임을 명시한다. 배포본에는 지원 실행 파일/환경과 확인된 구간, 미해결 문제가 표시되어야 한다.

## 11. 빌더에게 위임하는 결정

RE8의 실제 함수·객체·필드·패턴, 필요한 훅 수, 초기 실험 상수, 코드 파일 분할, 구체적인 ABI 브리지와 동기화 방식은 증거를 바탕으로 결정한다. 구조체 이름과 주소를 추측해 설계의 확정 사실로 만들지 않는다.

기본 언어/패키지 구조와 작은 UI 연결 방식은 구현 계획에서 구체화할 수 있다. 광원 제어를 다시 Lua 실험 중심으로 바꾸거나, 셰이더 교체·3인칭 등으로 범위를 넓히는 결정은 이 문서의 위임 범위에 포함되지 않는다.
